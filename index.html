The last twenty minutes

If there is time for one pass only, make it this one. Every line is something that can be written as a question directly, in class order, with no elaboration — the detail is all below.

  1. SQL was SEQUEL, by Chamberlin and Boyce at IBM. Renamed before commercial release in 1979; ANSI 1986, ISO 1987.
  2. Four SQL groups: DDL (CREATE/ALTER/DROP) · DML (SELECT/INSERT/UPDATE/DELETE) · DCL (GRANT/REVOKE) · Transaction (COMMIT/ROLLBACK/SAVEPOINT).
  3. The three requirements: Data Persistency · System Reliability · Scalability.
  4. Data Administrator = Plan, Define, at the start. Database Administrator = Config, Maintain/Tune, at the end.
  5. The stage sequence: System Planning → System Definition → Requirement Collection → Database Design → Implementation → Maintenance.
  6. Meta-data = the description of the data, in the DBMS catalog, also called the data dictionary or system catalog. Stored separately from the data.
  7. ANSI-SPARC = External / Conceptual / Internal, proposed 1975, and never a formal standard. ANSI = American National Standards Institute; SPARC = Standards Planning And Requirements Committee.
  8. The DBMS owns external + conceptual + internal. The OS owns only the real files on disk.
  9. Data independence = a schema at an upper level is unaffected when a lower one changes.
  10. Three design stages: Conceptual → ER diagram · Logical → tables and constraints · Physical → files, indexes, partitions. Everything starts from Requirement Collection and Analysis.
  11. Five data models: Hierarchical → Network → Relational → Object-oriented → Object-relational. A data model has three parts: structural, manipulative, integrity constraint.
  12. Architectures: Teleprocessing → File-Server → Two-tier (fat client) → Three-tier (thin client, easier load balancing, more modular). ODBC = Microsoft; JDBC = Java.
  13. The relational model: Codd, IBM Research, 1970, CACM June 1970, won the ACM Turing Award. Built on set theory.
  14. The pairs: Relation=Table · Attribute=Column · Tuple=Row · Schema of a relation=Table definition · Domain=all possible column values.
  15. Cardinality = rows (changes with the instance). Degree = columns (fixed by the schema). Both mean something else entirely in class 4.
  16. Relation properties: one atomic value per cell · no duplicate tuples · row order does not matter · column order does, on an INSERT that names no columns.
  17. Key hierarchy: Superkey ⊃ Candidate (uniqueness + irreducibility) → one becomes Primary → the rest are Alternate. Several attributes = composite; invented = surrogate.
  18. Entity integrity: every relation has a PK and it may never be null. Referential integrity: an FK matches an existing PK, or is null. General: Unique, Check, Not Null.
  19. Referential actions: writing nothing = RESTRICT (the default) · CASCADE deletes on through · SET NULL nulls the child FK (that column must not be NOT NULL). None of them help an INSERT.
  20. Who violates what: INSERT = every kind · DELETE = referential integrity only · UPDATE = domain/NOT NULL of the attribute changed, and more if it is a PK or FK.
  21. The ER model is top-down — entities and relationships first, attributes after. Bottom-up starts at the attributes.
  22. Three components: Entity Type (a rectangle) · Attribute · Relationship Type (a line that must be named). An attribute may belong to a relationship too.
  23. Degree of a relationship = how many entities · 2 binary (most common) · 3 ternary · 4 quaternary · looping back = recursive = where SELF JOIN comes from.
  24. Attributes on three axes: Single↔Composite (components) · Single-valued↔Multiple-valued (several at once) · Derived (computed, possibly from another entity).
  25. Notation: {PK} primary key · /x derived · indentation = composite · [1..3] multi-valued. The line's name is required; the arrow is not.
  26. A conceptual diagram carries primary keys only — no FKs, no unique/check/not null.
  27. min..max · min = participation (0 optional, 1 mandatory) · max = cardinality (1 or many). Reading A→B, look at the number on B's side.
  28. Naming 1:1 / 1:* / *:* uses the max on both sides only — ignore min.
  29. Strong has its own PK. Weak does not, and borrows the strong entity's PK through an identifying relationship into a composite key (or you invent a surrogate key instead).
  30. A relationship's attributes: if the data exists only once the relationship occurs, hang it off the line with a dashed line into a box with a blank header.
  31. Constraints come from the business requirements, not from the designer. Fill gaps only where the brief is silent.
  32. The exam: week 6, theory only, 30%. Quiz#1 is cancelled. ER must use the UML notation from the slides — not MySQL Workbench.

The pairs that get confused

A theory paper is mostly a vocabulary test, and the words that cost marks are the ones that look alike but mean different things. Read these before working through W1–W5.

Cardinality (W3 vs W4)
class 3: the number of rows in a relation. class 4: the max half of a multiplicity — at most how many. Same word, unrelated meanings.
Degree (W3 vs W4)
class 3: the number of columns a relation has. class 4: the number of entities taking part in a relationship (2 = binary, 3 = ternary).
Data vs Database Administrator
Two different roles despite the names. The Data Administrator plans and defines the system at the start (Plan, Define); the Database Administrator configures and maintains it at the end (Config, Maintain/Tune).
Superkey / Candidate / Primary
Superkey identifies a row and may carry surplus attributes. Candidate is a superkey that cannot be reduced further. Primary is the candidate that was chosen; the rest become alternate keys.
min .. max
The first number (min) is participation — is it compulsory? (0 = optional, 1 = mandatory). The second (max) is cardinality — if it exists, how many at most?
Composite vs Multi-valued
Composite = one value made of several components (address = street + city + postcode). Multi-valued = several values at the same moment (three phone numbers). Different axes entirely.
Strong vs Weak entity
Strong = has a primary key of its own and borrows from nobody. Weak = cannot identify itself from its own attributes, so it borrows the strong entity's PK into a composite key through an identifying relationship.
Entity vs Referential integrity
Entity integrity: every relation must have a primary key and it may never be null. Referential integrity: a foreign key's value must match an existing primary key, or be wholly null.
ER vs Instance Diagram
ER Diagram = the schema — boxes, lines, attributes, at design time. Instance Diagram = the actual stored data and the links between values, once the system is running.
Bottom-up vs Top-down
Bottom-up starts at the attributes (a receipt in your hand, picked apart). Top-down starts at the entities (the big picture, refined downward). The ER model is top-down.
ANSI-SPARC
The three-level architecture — External / Conceptual / Internal — proposed in 1975. It never became a formal standard, yet it is still the basis for understanding how a DBMS works.
Derived attribute
An attribute computable from others, not necessarily in the same entity type. Written with a leading slash: /totalAmount.
W1

Introduction to Database

6 Aug 2026 What a database is, how it differs from a pile of files, and who does what around it.

SQL, in four groups

DDLData Definition — CREATE, ALTER, DROP
DMLData Manipulation — SELECT, INSERT, UPDATE, DELETE
DCLData Control — GRANT, REVOKE
TransactionCOMMIT, ROLLBACK, SAVEPOINT, SET ISOLATION
  • Originally SEQUEL (Structured English Query Language), by Donald Chamberlin and Raymond Boyce at IBM in the 1970s; renamed SQL before commercial release in 1979.
  • Standardised by ANSI in 1986 and by ISO in 1987.

What makes it a database system

  • Self-describing — the DBMS catalog stores the structure, data types and constraints. That is the meta-data.
  • Program-data independence — the structure or storage format can change without rewriting the programs.
  • Data abstraction — the data model hides the real storage details.
  • Multiple views — each group of users sees only the slice it cares about.
  • Multi-user — concurrency control keeps it correct when many work at once, and the recovery subsystem guarantees a finished transaction is recorded permanently.

Watch out

  • Data Administrator ≠ Database Administrator. Nearly the same name, different jobs: the first plans and defines at the start, the second configures and maintains at the end.
  • The three requirements come as a set: Data Persistency (data outlives the program that made it), System Reliability (correct and fast recovery), Scalability.
  • The main sequence in the Actors diagram: System Planning → System Definition → Requirement Collection → Database Design → System Implementation → System Maintenance.

Database Environment & Architecture

13 Aug 2026 The three levels that separate what a user sees from what is actually stored — and why that separation is worth having.

Database design, three stages

1 Conceptualindependent of any DBMS → an ER Diagram
2 Logicaldepends on implementation → tables and constraints
3 Physicalhow it is stored for efficient access → files, indexes, partitions
  • It all starts from Requirement Collection and Analysis, before stage 1.
  • The slide's analogy: a 2D floor plan is the conceptual/logical model; a 3D model with real materials and colours is the physical one.

Multi-user architectures

Teleprocessingone powerful central machine with many "dumb" terminals; the load all falls centrally
File-Serverthe server does nothing but serve files; a full DBMS on every workstation and a great deal of data crossing the network
Two-Tierclient presents and runs the logic (a fat client); server serves data
Three-Tierthin client · application server holds the business logic · database server holds the data

Watch out

  • Five kinds of data model, in the slide's order: Hierarchical (a tree, one parent) → Network (a many-to-many graph) → Relational (plain tables) → Object-oriented → Object-relational.
  • A data model is defined in three parts: a structural part, a manipulative part, and an integrity constraint part.
  • ODBC is Microsoft's; JDBC is Java's. Both are database-oriented middleware.
  • Three-tier's advantages, often asked: cheaper hardware, one place to maintain the logic, modularity, and easier load balancing.

The Relational Model

20 Aug 2026 The heaviest vocabulary of the five weeks, and the richest ground for a theory paper. The lecturer opened it herself: "today we will also come to understand the relational model through its vocabulary." Where these constraints get written as SQL is a band of its own, further down. Note: the notes behind this band were taken in the Wednesday (G1) session on 19 Aug, not the Thursday one — the slides are the same, but anything said off-slide may have differed.

Formal ↔ informal terms

RelationTable
AttributeColumn / Field
TupleRow / Record
Domainall possible column values
Schema of a RelationTable Definition — R(A1, A2, …, An)
Cardinalitythe number of rows — changes with the instance
Degreethe number of columns — fixed by the schema

Properties of a relation

  • Its name is distinct from every other relation.
  • Every cell holds exactly one atomic value — it cannot be broken down further.
  • All values of one attribute come from the same domain.
  • No duplicate tuples.
  • Row order does not matter, but column order does — a tuple is an ordered list of values.
  • null is the special value meaning unknown, not available, or inapplicable to that tuple.

Watch out

  • The slides look self-contradictory — slide 6 says attribute order is irrelevant, property 7 says it matters. They do not actually conflict. In set theory a relation is a set of attributes, so order is meaningless; in practice an INSERT naming no columns must list values in the declared order or the data lands in the wrong columns.
  • A slide typo: STUDENTS says "four attributes" then lists five. Five is correct (degree = 5).
  • In the terminology figure, cardinality = 4 and degree = 5 are measured on PrivateOwner, not PropertyForRent (which has 6 rows and 8 columns). An exam question will use that.

ER Model (1/3) — Conceptual Design

27 Aug 2026 From "what a table looks like" to "how you design one before it exists". The lecturer repeated many times that the notation must be the one in the slides — UML notation — in the lab, the project, and the exam.

Three components, and degree

Entity Typethings with the same properties — drawn as a rectangle
Attributea property of an entity type or of a relationship
Relationshipa connecting line that must always be named — usually a verb
Binary (2)the most common
Ternary (3)Staff–Branch–Client via Registers
Quaternary (4)Solicitor–Buyer–FinancialInstitution–Bid
Recursiveloops back to the same entity — where SELF JOIN comes from

Attributes, on three axes

  • Components — Single (staffNo) vs Composite (name = fname + lname).
  • Values — Single-valued vs Multiple-valued: INT207's requisiteCourseNos holds both INT102 and INT203.
  • Where the value comes from — Derived, computed from others possibly in another entity: /totalAmount on Orders comes from /amount on Order_Items.
  • A relationship's attributes: if the data can only exist once the relationship occurs (dateAdvert, cost), hang it off the line with a dashed line into a box whose header is deliberately blank.

Watch out

  • Multiple-valued means several values at the same moment. Changing your name is not multi-valued — at any one time you have exactly one name. The lecturer set this trap deliberately.
  • To name a relationship 1:1 / 1:* / *:*, look only at the max on both sides and ignore min entirely.
  • The constraints are not yours to invent — they come from the business requirements. Only where the brief is silent or unclear may you fill in the gaps.
  • The same pair of entities may carry several relationship lines if each means something different (Staff–Branch has both Manages and Has) — and then each end needs a role name.

ER Model (2/3) — turning a brief into a diagram

3 Sep 2026 No new concepts — class 4's ideas applied to a bigger brief. Both directions are practised: bottom-up from a page of a recipe book, and top-down from a library-system brief. Source: LAB05 Conceptual Database Design 2.

Bottom-up practice

  • The brief: one page from Ralph's Raving Recipes. A publisher wants the recipes on the web, easily searchable.
  • Three steps: 1) list every type of information on the page, 2) group them into entities and attributes, 3) name the relationships and draw the ER diagram with primary keys, in UML notation.
  • This is exactly the "receipt" analogy from class 4 — you are handed one document and pick the small pieces of data out of it before grouping them.

Top-down practice

  • The brief: a university library management system, its requirements collected by interviewing the library staff.
  • Six sections: Members · Library branches · Staff · Books · Loans · Reservations.
  • It exercises every class 4 concept — composite, multi-valued, derived, two relationships between the same pair, an *:* carrying attributes, and a 0..1. The table below is the decoder for those sentences.

Watch out

  • "Left empty and filled in later" is not multi-valued. A return date that is blank while the book is out is an ordinary nullable attribute. Multi-valued means several values at the same moment.
  • "Must never be stored, work it out when needed" = derived. Current age, books currently on loan, and whether a loan is overdue — the brief forbids storing all three. Write them with a leading /.
  • Staff and Branch carry two relationships — which branch someone works at, and who manages a branch, are different facts. Two lines, with role names. The same shape as Manages/Has on the class 4 slide.
A worked ER diagram for LAB05's top-down brief — the university library system
Reading all six lines Staff 1..1 — Manages ▶ — 0..1 Branch. One branch must have a manager, and exactly one (read the number on Staff's side). One member of staff need not manage a branch, but manages at most one if they do (read Branch's side) — that is "most staff manage no branch at all".
Borrows Member 0..* — Borrows ▶ — 0..* Book is *:*, from "many books over time" and "many members over time". Both minimums are 0 because "a newly registered member may have borrowed nothing" and "a newly catalogued book may never have been borrowed".
Places and For Member 1..1 — Places ▶ — 0..1 Reservation — the 0..1 on Reservation's side is "one member may hold at most one active reservation". And Reservation 0..* — ◀ For — 1..1 Book, because one reservation names exactly one book while one book may be reserved many times.
Three places where we decided, because the brief does not say
  • WorksAt carries 1..* on Staff's side. The brief only says "one branch may have many staff" and never says whether a branch may have none. We chose 1..* because every branch must have a manager, who is a member of staff. 0..* is defensible too — but you must be able to justify it, which is exactly the lecturer's rule about filling silent gaps.
  • Loan is drawn as a relationship carrying attributes, not as an entity. That is how class 4 taught a *:* with attributes (Newspaper–Advertises–PropertyForRent). Drawing Loan as its own entity is not wrong either — it then becomes a weak entity borrowing a PK from both Member and Book.
  • "Must not borrow the same book twice on the same day" is not on the diagram. A conceptual diagram carries primary keys only — no unique, no check. That rule appears at the logical stage in week 8, as the composite primary key of the Loan table: (memberID, ISBN, dateBorrowed), which enforces it for free.

Which statement fails, and why — LAB02 Q6

The lab gives four bad statements, each violating a different constraint. It is the sharpest discriminator you will meet.

INSERT
'CS203'		no such course exists → referential integrity — the FK points at a PK that is not there
INSERT
grade 'H'		H is not in the permitted grade list → CHECK, a domain constraint
DELETE
student 66001		enrollment rows still reference it → referential integrity from the other side, refused because the default is RESTRICT
UPDATE
credits = 8		credits must be 1–6 → CHECK. Proof that an UPDATE violates a domain too, not only an INSERT
Note that the first two are both INSERTs yet violate different kinds, and the last two confirm this board's table: DELETE can only violate referential integrity, while UPDATE violates the domain of the column it changed.

Naming a constraint — LAB03

the ruleEvery constraint you create must be given an explicit name using the CONSTRAINT keyword
the pattern<prefix>_<table>_<column> · all lowercase · underscores, no spaces · at most 64 characters
if you don'tMySQL/InnoDB names it <table>_ibfk_<n> — ibfk is InnoDB foreign key, and n is that FK's position in the table
A name you chose is readable when an error comes back; enrollment_ibfk_1 tells you nothing. And you cannot DROP CONSTRAINT without knowing its name — which is the real reason to name them yourself.

The lab counts five groups; the slides count four

Only the grouping differs, not the content — but if a question asks how many kinds there are, you need to know which framing it is using.

slidesKey · Entity integrity · Referential integrity · General (Unique, Check and Not Null together) = 4

theory

The facts most easily turned into an exam question

This paper is theory only — no practical half. What that can test is definitions, confusable pairs, tables with a clear ordering, and reading a diagram. Everything below comes from the slides or from what was said in class.

Integrity constraints, four groups — class 3

The purpose of all of them: to prevent accidental damage to the data.

Keythe set of attributes that identifies each tuple uniquely
Entity integrityevery relation must have a primary key, and a primary key may never be null
Referential
integrity		an FK's value must match a primary key that actually exists in the referenced relation, or be wholly null
GeneralUnique, Check, Not Null — extra rules set by a user or the DBA for a business condition, such as Check (salary > 15000)
"Or be null" applies only when that FK column is not declared NOT NULL — and if you intend to use ON DELETE SET NULL, that column must never be NOT NULL.

Referential actions — class 3

What happens when an UPDATE or DELETE touches a parent key that child rows still reference.

RESTRICTrefuses the delete or update. Naming RESTRICT is the same as writing nothing — it is the default (NO ACTION likewise)
CASCADEdeletes or updates the parent, then does the same to the matching child rows
SET NULLdeletes or updates the parent, then sets the child rows' FK column to NULL
The trap: a referential action does nothing for INSERT. ON DELETE/ON UPDATE govern only what happens to child rows when a parent is deleted or updated. Inserting a child row pointing at a key that does not exist is refused regardless of which action is set.

Which operation can violate what — class 3

An asymmetric table with a clear pattern — ideal multiple-choice material.

INSERTcan violate every kind — domain, key, referential integrity, entity integrity
DELETEcan violate referential integrity and nothing else — when the PK of the row being deleted is still referenced
UPDATEviolates the domain and NOT NULL of the attribute changed, and possibly more depending which — especially changing a PK (children lose their parent) or an FK (it may point at nothing)
For DELETE, one of three must be chosen at design time, for every foreign key: RESTRICT refuses, CASCADE deletes on through, SET NULL sets the referencing FK to null.

The ones people get wrong
Mixing up the two cardinalities Class 3's cardinality is the number of rows; class 4's is the max half of a multiplicity. Degree does the same thing: class 3 means columns, class 4 means how many entities take part. Both weeks sit on the same paper.
Reading the number on the wrong side She said outright this is the mistake students make most. Reading from A to B, look at the number on B's side, not A's, and open the sentence with "one A …".
Putting foreign keys on a conceptual diagram This stage carries primary keys only — no FKs, no unique, no check, no not null, because implementation has not been reached. It asks only what the main data is, how it relates, and what the primary key is.
Expecting a referential action to help an INSERT ON DELETE/ON UPDATE govern only what happens to child rows when a parent is deleted or updated. Inserting a child pointing at a key that does not exist is refused whatever you set.
Thinking a changed value is multi-valued Multiple-valued means several values held at the same moment — three phone numbers. Changing your surname is not: at any one time you have exactly one.
Using min to name a 1:1 or 1:* To call something one-to-one / one-to-many / many-to-many, look at the max on both sides only. 0..1 ↔ 0..* is still one-to-many even though both mins are zero.

Keys and integrity constraints — class 3

Delete a parent row that children still reference Refused. Referential integrity. A foreign key's default is RESTRICT, which is what writing no ON DELETE at all means. Fix: DROP the constraint and ADD it back with ON DELETE CASCADE or ON DELETE SET NULL.
Insert a child whose FK points at a PK that does not exist Always refused. Referential integrity. No referential action helps here — ON DELETE/ON UPDATE govern only what happens to child rows when a parent is deleted or updated. Fix: create the parent row first.
Put a null in a primary key column Refused. Entity integrity — every relation must have a primary key and it may never be null. A different rule from referential integrity, which is the commonest distractor for it.
Use ON DELETE SET NULL on a NOT NULL column Will not work. The action must write a null into a column that forbids one. The slide warns about this itself. Fix: drop the NOT NULL, or use RESTRICT/CASCADE instead.
Change the primary key of a parent that has children The children lose their parent. The same referential-integrity violation as a delete, governed by ON UPDATE, which has the same three actions. Careful: the slide warns against defining several ON UPDATE CASCADE rules acting on the same column from both sides.
Create a table whose FK points at a table that does not exist yet Cannot be done. The referenced table must exist first. And where two tables reference each other (EMPLOYEE ↔ DEPARTMENT), no ordering completes both in one pass. Fix: create one without its FK, then add it afterwards with ALTER TABLE … ADD FOREIGN KEY.
Add a constraint later with ALTER TABLE when existing rows break it Errors out. Existing rows must already satisfy it. Fix: UPDATE the existing data first, then add the constraint — not INSERT, since the rows are already in. Better still, declare constraints at CREATE TABLE time.
Insert without naming columns, in your own order The data lands in the wrong columns. A tuple is defined as an ordered list of values, so the order must match the CREATE TABLE declaration. This is why property 7 says column order matters while slide 6 says attribute order does not — two angles, not a contradiction.

Definitions and architecture — classes 1–2

Change the internal storage and assume the users' views must change too They do not. That is the whole of data independence — an upper schema is unaffected when a lower one changes. Add an index at the internal level and no view need know; the DBA can change the conceptual structure without disturbing anyone.
Say the internal level is the OS's job Wrong. The DBMS owns external + conceptual + internal; only the real files on disk are the OS's. The internal schema is the description of how it is stored, not the files — a strong distractor because it sounds like hardware.
Call ANSI-SPARC an ANSI or ISO standard Wrong. The slide says it never became a formal standard, though it remains the basis for understanding a DBMS. The 1986/1987 ANSI/ISO dates belong to SQL, a different matter.
File GRANT / REVOKE under DDL Wrong group. Both are DCL (Data Control Language), which governs privileges. DDL is CREATE/ALTER/DROP; DML is SELECT/INSERT/UPDATE/DELETE; COMMIT/ROLLBACK/SAVEPOINT are Transaction Control.
Swap Data Administrator and Database Administrator Two different roles. Data Administrator does Plan and Define, at the start. Database Administrator does Config and Maintain/Tune, at the end. The names are close enough to make an excellent distractor.

A relation holds 6 tuples and 8 attributes. What is its degree?

  2. 8
  3. 48

Which is not a property of a relation?
  1. Each cell holds exactly one atomic value
  2. There are no duplicate tuples
  3. The order of the tuples matters
  4. All values of one attribute come from the same domain
tap for the answer

Row order does not matter — a relation is a set of tuples, and reordering them leaves the same relation. What does matter is column order, because a tuple is defined as an ordered list of values, so an INSERT naming no columns must follow the declared order. This is the point where the slides look self-contradictory but are speaking from two angles.

A superkey none of whose proper subsets is itself a superkey is called a…
  1. Primary key
  2. Candidate key
  3. Alternate key
  4. Composite key
tap for the answer

That is the irreducibility property, which together with uniqueness defines a candidate key. A primary key is the candidate that was chosen; an alternate key is one that was not. A composite key describes a key built from several attributes — a different axis of classification altogether.

What does the entity integrity constraint state?
  1. An FK's value must match an existing PK, or be null
  2. Every relation must have a primary key, and it may never be null
  3. Every cell must hold an atomic value
  4. A value must lie within its attribute's domain
tap for the answer

The first option is referential integrity — the strongest distractor, because the two are routinely swapped. The third is a property of a relation, not an integrity constraint. The fourth is a domain constraint.

A foreign key with no ON DELETE clause behaves the same as which action?
  1. RESTRICT
  2. CASCADE
  3. SET NULL
  4. SET DEFAULT
tap for the answer

RESTRICT is the default, so writing it and writing nothing are identical (NO ACTION likewise). To make it cascade you must DROP the constraint and ADD it back with ON DELETE CASCADE. MySQL Workbench shows this plainly — the Related Tables panel reads On Update: RESTRICT / On Delete: RESTRICT.

Which integrity constraint can a DELETE violate?
  1. Domain constraint
  2. Entity integrity
  3. Referential integrity
  4. All of them
tap for the answer

A DELETE puts no new value in, so it cannot violate a domain, a key, or entity integrity. The only way it can go wrong is when the PK of the removed row is still referenced. The last option is the answer for INSERT, which can violate every kind.

  3. 4 — quaternary
  4. It depends on how many attributes it has
tap for the answer

A relationship's degree is how many entities take part — three here, so ternary. One registration must record all three things: which client, with which member of staff, at which branch. The last option is a distractor trading on class 3's degree of a relation, which counts columns.

In the multiplicity 0..*, what does the 0 tell you?
  1. Participation — taking part is optional
  2. Cardinality — at most zero occurrences
  3. That the relationship is one-to-many
  4. That the attribute may be null
tap for the answer

min..max, always. min = participation — is it compulsory? (0 = optional, 1 = mandatory). max = cardinality — if it exists, how many at most? The second option swaps the two. The third is wrong because naming 1:1 / 1:* / *:* uses the max on both sides, not this one number.

  3. A derived attribute computed from three others
  4. The multiplicity of a relationship

Square brackets after an attribute name are the notation for a multi-valued attribute, read as "at least 1 number, and at most 3 stored". Composite uses indentation under a parent attribute; derived uses a leading /; and a multiplicity is written on the line between boxes, not after an attribute name.
